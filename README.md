# FileCollector

Потокобезопасный класс, который собирает файлы из чанков. Чанки приходят в любом порядке,
могут пересекаться и повторяться, а один файл одновременно собирают несколько потоков.

## Сборка и тесты

Нужны CMake ≥ 3.20 и компилятор с C++20 (проверено на Visual Studio 2022).
GoogleTest скачивается сам при первой настройке.

```sh
cmake -B build -S .
cmake --build build --config Debug
ctest --test-dir build -C Debug
```

**Проверка гонок данных:**

```sh
cmake -B build-tsan -S . -DCMAKE_BUILD_TYPE=Debug -DFC_TSAN=ON
cmake --build build-tsan
setarch "$(uname -m)" -R ctest --test-dir build-tsan
```

`setarch -R` отключает перемешивание адресов для запуска: без него TSan в g++ 13 на свежих ядрах падает с `unexpected memory mapping`, не дойдя до тестов.

## Интерфейс

```cpp
FileCollector fc;
fc.CollectFile(id, size);                 // зарегистрировать файл
fc.OnNewChunk(id, pos, std::move(bytes)); // добавить чанк
FileData f = fc.GetFile(id);              // весь файл без копии; false, если ещё не собран
std::size_t n = fc.Read(id, pos, out);    // сколько байт подряд уже есть с pos — скопировать в out
fc.RemoveFile(id);                        // освободить память
```

`FileData` - указатель на неизменяемые байты (`shared_ptr<const uint8_t[]>`) и размер.
Байты живут, пока жив хоть один `FileData`, даже если файл уже удалён из коллектора.

Для "ещё не готово" исключений нет: это обычное состояние, о нём говорят сами ответы
(`GetFile` пустой, `Read` вернул 0). Исключение `FileCollectorError` с кодом - только для
ошибок использования (см. "Поведение на краях").

## Как устроено

**Хранение.** В `CollectFile` под файл сразу выделяется буфер полного размера, каждый новый байт копируется прямо на своё место. Собранный файл и есть этот буфер, поэтому отдаётся без копии.

**Учёт полученного**. `IntervalSet`: `std::map`  из непересекающихся участков `[begin, end)`. Пересекающиеся и стыкующиеся участки склеиваются, поэтому
на нормальных данных участков мало. По новому чанку `Gaps` находит только дыры:
дубликаты и уже полученные байты не копируются вовсе.

**Блокировки: три уровня, и ни один не держится на время копирования байт:**

1. *Реестр файлов* (`std::mutex`). Только чтобы найти или добавить файл. Состояние файла
   лежит в `shared_ptr`: поток берёт его копию и сразу отпускает замок реестра.
2. *Замок файла*. Охраняет только учёт: что записано (`done`) и что забронировано (`busy`).
3. *Бронирование.* Под замком файла поток находит дыры, вычитает из них то, что сейчас
   копируют другие потоки, и бронирует остаток. Отпускает замок. **Копирует без замка** -
   эти байты принадлежат только ему. Снова берёт замок, снимает бронь и отмечает
   байты записанными.

**Чтение без замка.** Записанный байт больше никогда не меняется: по условию содержимое
файла неизменно, а бронирование не пускает второго писателя на занятые байты. Поэтому
`Read` под замком только узнаёт, сколько байт подряд уже записано, а копирует после.
Видимость гарантирует сам замок: писатель отметил байты записанными под ним, читатель
прочитал отметку под ним же.

**Флаг «собран»** — `std::atomic<bool>`: писатель ставит его с
`memory_order_release`, `GetFile` читает с `memory_order_acquire`. Видишь `true` — видишь и все байты, и после этого
в буфер больше никто не пишет.

## Решения и почему

| Решение | Альтернатива | Почему не она |
|---|---|---|
| `std::map` участков | Флаг на каждый байт | Проход по каждому байту чанка и всегда `size/8` памяти |
| Копирование вне замка | Копия под замком файла | Под замком потоки одного файла копируют строго по очереди |

## Поведение на краях

| Ситуация                                           | Что происходит                                            |
| -------------------------------------------------- | --------------------------------------------------------- |
| Чанк или чтение для незарегистрированного `fileId` | `FileCollectorError::UnknownFile`                         |
| Чанк вылезает за размер файла                      | `OutOfRange`                                              |
| Повторный `CollectFile`                            | Тот же размер - ничего не делает; другой - `SizeMismatch` |
| Пустой чанк                                        | Игнорируется (границы всё равно проверяются)              |
| Файл размером 0                                    | Собран сразу после `CollectFile`                          |
| Чанк после того, как файл собран                   | Игнорируется как дубликат (границы проверяются до этого)  |
| Слишком много разрозненных участков                | `TooFragmented`                                           |

## Сложность

n — число участков в учёте файла, k — сколько из них задевает чанк, L — новых байт в чанке.

| Операция      | Время                   | Под замком файла    |
| ------------- | ----------------------- | ------------------- |
| `OnNewChunk`  | O(log n + k + L)        | только O(log n + k) |
| `Read`        | O(log n + длина)        | только O(log n)     |
| `GetFile`     | O(1)                    | нет                 |
| `CollectFile` | O(1) + выделение памяти | выделение без замка |


## Тесты

30 тестов на GoogleTest, все проходят и под ThreadSanitizer.

- `IntervalSetTest` — склейка, вложенные и стыкующиеся участки, дыры, а также сверка
  на 3000 случайных участков с простым эталоном «флаг на байт».
- `FileCollectorTest` — пример из ТЗ, обратный порядок, дубликаты, все края из таблицы выше,
  частичное чтение, удаление файла, на который ещё держат `FileData`.
- `FileCollectorThreadsTest` — 8 потоков собирают один файл из пересекающихся кусков;
  16 файлов параллельно; чтение во время записи (каждый прочитанный байт сверяется, `GetFile`
  не имеет права отдать файл раньше времени); гонка регистраций одного id; удаление файла,
  пока в него пишут.



## Ограничения

- **Предел числа участков** `maxRangesPerFile`, по умолчанию 2^20. Защита от враждебного порядка чанков: куски по байту через байт раздувают
  дерево на порядки больше самого файла. На пределе пропускаются только чанки, которые
  касаются уже полученного (они заполняют дыры, а не плодят участки), поэтому файл
  всё равно можно дособрать.
